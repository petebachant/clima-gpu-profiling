# Redundant saturation work in the SGS microphysics kernels, and the cliff at 128 registers

The SGS node path of `microphysics_tendencies_1m` computed two saturation specific humidities per node and threw both away: the conditional node carried a total water that no production path read, and the node function recomputed the saturation `_point_value` had just evaluated at the same temperature, density and parameters.
Of the <!-- calkit value key=work.calls_before path=results/experiments/quadrature-saturation/stats.json -->40<!-- /calkit value --> saturation evaluations a cloudy cell performed there, <!-- calkit value key=work.calls_removed path=results/experiments/quadrature-saturation/stats.json -->24<!-- /calkit value --> were dead or duplicated, leaving the <!-- calkit value key=work.calls_after path=results/experiments/quadrature-saturation/stats.json -->16<!-- /calkit value --> that have to happen --- one per temperature point, each at its own temperature.
Removing them is bit-for-bit, and the compile-only probe measures it that way: every variant produces the same hash of every output bit of <!-- calkit value key=probe_summary.points path=results/experiments/quadrature-saturation/stats.json -->4368384<!-- /calkit value --> points.

What the experiment then found is that the arithmetic saving is not the thing that decides the outcome.
`ClimaCore` sizes a slice loop's grid from its register count, and the environment quadrature broadcast compiles to exactly the top of its occupancy band, so it has no register headroom at all --- it loses a quarter of its resident warps for one extra register.
Deleting the unread field perturbs the allocation by two registers, and that is enough: the same removal that makes the instantaneous sibling <!-- calkit value key=profiled.both_removals.implicit_tendency.change_pct path=results/experiments/quadrature-saturation/stats.json -->-34.85<!-- /calkit value -->% faster by taking it up a band makes the quadrature broadcast <!-- calkit value key=profiled.both_removals.quadrature_cache.change_pct path=results/experiments/quadrature-saturation/stats.json -->7.41<!-- /calkit value -->% slower by taking it down one, while both do strictly less work.
Reusing the saturation is register-neutral by contrast, so applied on its own it is a smaller saving that costs nothing anywhere --- <!-- calkit value key=profiled.saturation_reuse.device_change_ms path=results/experiments/quadrature-saturation/stats.json -->-102.1<!-- /calkit value --> ms over the device with every kernel left in its band --- and the choice between the two is the result this document ends on.

## Why this experiment declares no profiling stages

It reads the pipeline's own arm profiles rather than taking its own pair, because the treatment changes one arm and the pipeline already profiles exactly that arm.
Those profiles are transient --- the next experiment overwrites `results/nsys/mod.sqlite` --- and this experiment needs to compare several variants of one treatment, which a single shared path cannot hold.
So `scripts/snapshot-quadrature-profile.py` is run by hand after each profiling pass and accumulates one entry per ClimaAtmos revision in `results/quadrature-profiles.json`, the way `scripts/measure_occupancy.py` writes `results/launch-inventory.json` and for the same reason; the analysis below reads that file and never the databases.

Every comparison is **within the mod arm**, against this arm before the treatment, rather than against the baseline arm.
The two arms also differ by the sedimentation fold, which edits the same file the treated broadcast lives in, so a cross-arm comparison carries a standing difference and --- because a kernel's name embeds the source line of the statement that built it --- silently fails to pair the kernels at all.
The pre-treatment entry is transcribed from `results/launch-inventory.json`, whose profile has since been overwritten; it is the same arm at the same revision, <!-- calkit value key=provenance.pre_treatment_commit path=results/experiments/quadrature-saturation/stats.json -->9eb34e31a<!-- /calkit value -->.

## Why the lever here is arithmetic and not occupancy

A kernel's register count is the largest frame on its call graph rather than the sum of its parts, because the node function is `@noinline` and `ptxas` allocates for the peak.
A barrier can therefore split a frame but never shrink one, which makes the largest frame reachable from ClimaAtmos the floor of every barrier arrangement available --- and that floor is measurable by passing stubs, with no edit to ClimaAtmos at all, since `sum_over_conditional_nodes` takes the node function as an argument.

The census puts the whole kernel at <!-- calkit value key=frames.whole_kernel_registers path=results/experiments/quadrature-saturation/stats.json -->130<!-- /calkit value --> registers, the traversal with a stub node function at <!-- calkit value key=frames.traversal_registers path=results/experiments/quadrature-saturation/stats.json -->84<!-- /calkit value -->, the real node function at <!-- calkit value key=frames.node_function_registers path=results/experiments/quadrature-saturation/stats.json -->112<!-- /calkit value -->, and CloudMicrophysics' substep-averaged bulk tendency on its own at <!-- calkit value key=frames.bmt_registers path=results/experiments/quadrature-saturation/stats.json -->102<!-- /calkit value -->.
ClimaAtmos's entire reconstruction is therefore worth <!-- calkit value key=frames.climaatmos_registers path=results/experiments/quadrature-saturation/stats.json -->10<!-- /calkit value --> registers on top of the package it calls, and the next step up needs <!-- calkit value key=frames.step_to_gain_registers path=results/experiments/quadrature-saturation/stats.json -->96<!-- /calkit value --> or fewer, which the bulk tendency misses on its own by <!-- calkit value key=frames.bmt_over_step path=results/experiments/quadrature-saturation/stats.json -->6<!-- /calkit value -->.
So the bulk tendency by itself already runs at <!-- calkit value key=frames.bmt_warps_per_sm path=results/experiments/quadrature-saturation/stats.json -->16<!-- /calkit value --> warps per multiprocessor, which is what the whole kernel gets today, and a ClimaAtmos-side register treatment that removed every register ClimaAtmos owns would land in the band it started in.
That is why this experiment went after the kernel's arithmetic instead, and the irony of the result is that the arithmetic change moved the registers anyway.

## What was removed

**The node carried a total water that nothing read**, one saturation evaluation for each of the rule's <!-- calkit value key=work.nodes path=results/experiments/quadrature-saturation/stats.json -->8<!-- /calkit value --> nodes.
`ConditionalNode` held a `q` field, set by `_conditional_node` from a `TD.q_vap_saturation` call at the node temperature, and no production code path ever read it --- only two test assertions did.
It is a leftover from before the temperature-point split: `_point_value` now sets the state the evaluator receives per temperature point, so a copy of it at the node temperature is both unused and, where there is no split, the same number.
Deleting the field also removes <!-- calkit value key=work.nodes path=results/experiments/quadrature-saturation/stats.json -->8<!-- /calkit value --> registers from the eight-node table, which is live across the whole integration, and it leaves `conditional_rule` a function of the Gaussian geometry alone: it no longer needs the thermodynamic parameters, the density or the mean excess to place its nodes.

**The node function recomputed the saturation the traversal had just evaluated.**
`_point_value` evaluates `TD.q_vap_saturation(thp, T_pt, ρ)` to build the point's total water, and the evaluator's first act was to call `TD.q_vap_saturation(tps, T_hat, ρ)` with `T_hat` bound to that same `T_pt`, the same density and the same parameters, to recover the saturation excess from the state it had just been handed.
Passing the value across the barrier instead removes up to <!-- calkit value key=work.points_max path=results/experiments/quadrature-saturation/stats.json -->16<!-- /calkit value --> evaluations per cell and takes the saturation computation's working set out of the frame that caps the kernel.
It is exact rather than nearly exact: the same float is reused in the same expression, so the reconstruction is not merely equivalent but identical.

## The cliff, which is the transferable finding

The quadrature broadcast compiles to <!-- calkit value key=cliff.kernel_registers path=results/experiments/quadrature-saturation/stats.json -->128<!-- /calkit value --> registers and its occupancy band ends at <!-- calkit value key=cliff.band_max_registers path=results/experiments/quadrature-saturation/stats.json -->128<!-- /calkit value -->.
Its headroom is therefore <!-- calkit value key=cliff.headroom_registers path=results/experiments/quadrature-saturation/stats.json -->0<!-- /calkit value --> registers: it is not merely register-limited, it is sitting on the edge, and one more register takes it from <!-- calkit value key=cliff.warps_in_band path=results/experiments/quadrature-saturation/stats.json -->16<!-- /calkit value --> warps per multiprocessor to <!-- calkit value key=cliff.next_band_down_warps path=results/experiments/quadrature-saturation/stats.json -->12<!-- /calkit value -->.
Any change to this kernel --- including changes that unambiguously remove work --- has to be priced on its register count before its arithmetic, and an instrument whose register reading is off by <!-- calkit value key=probe_summary.error_registers path=results/experiments/quadrature-saturation/stats.json -->2<!-- /calkit value --> cannot do it.
This is the practical content of the launch model: when the grid is derived from the register count, a register is not a resource to economize but a step function, and a kernel at a band edge is a kernel where every change is an occupancy change.

## That the answer did not change

The probe hashes the raw bits of all four tendency components over the broadcast's whole output --- <!-- calkit value key=probe_summary.points path=results/experiments/quadrature-saturation/stats.json -->4368384<!-- /calkit value --> points of a varied state spanning clear, cloudy, mixed-phase and precipitating cells, on the model's own AMIP he16 layout.
The untreated arm, each removal alone and both together all produce the same hash, and so does the untouched sibling; the analysis asserts this rather than rendering it.
That is the reason to prefer these removals over the other lever on this kernel: the node count is how many points the quadrature evaluates, and changing it changes the answer, whereas neither of these can --- one deletes a field nothing reads and the other reuses a float already in a register.

## What is left

What remains of the quadrature kernel is the work it exists to do: up to <!-- calkit value key=work.points_max path=results/experiments/quadrature-saturation/stats.json -->16<!-- /calkit value --> evaluations of the 1M microphysics per cell, <!-- calkit value key=work.nodes path=results/experiments/quadrature-saturation/stats.json -->8<!-- /calkit value --> nodes each split at the freezing point, inside a package neither arm devs.
Lowering the node count is the largest single saving available on it and it is an accuracy decision rather than an implementation one.
Devving CloudMicrophysics would reach the <!-- calkit value key=frames.bmt_registers path=results/experiments/quadrature-saturation/stats.json -->102<!-- /calkit value --> registers of the bulk tendency, where the <!-- calkit value key=frames.bmt_over_step path=results/experiments/quadrature-saturation/stats.json -->6<!-- /calkit value --> registers between it and the next occupancy step are, and it rewrites the AMIP manifest and invalidates every profiling stage to try.
